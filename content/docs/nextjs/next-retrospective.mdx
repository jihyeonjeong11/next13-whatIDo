# Nextjs 프로젝트 처음 해본 후기


**Details**

9월부터 5개월 동안 SI 업체에서 금융 관련 프로젝트를 개발하며 겪은 경험을 반성해 본다.

SI 업체 및 프로젝트는 처음 해보았기 때문에 업무 프로세스에 잘 적응한 것 같지는 않지만, 여기서는 개발적으로만 이야기하기로 한다.

모든 프로젝트가 그랬지만, 힘든 점도 있었고 보람찼던 점도 있었다.

### Project Goal

- 해당 프로젝트는 한 금융사 웹페이지를 CRA에서 Nextjs로 교체하는 일이었다.
- 코어 라이브러리는 Nextjs, React 19, Next-Auth, React-Query.
- 백엔드와 존재하는 css 구조는 변환하지 않는다. 기존 전역 scss와 post로 되어 있는 백엔드는 유지 및 보수만 진행한다.

여기서 나는 전체적인 Nextjs 구조 작성을 담당했다. 러닝 커브를 최소화하고 개발 속도를 높이기 위해 최대한 react적인 구조를 작성하고, 외부 모듈과의 연결, 이후 메인 화면과 핵심 비즈니스 로직의 멀티-스텝 폼을 개발했다.

### Notable Use cases

1. 전역 scss 구조를 nextjs app router에서 사용하기. [nextjs - 오래된 sass 연결하기](/docs/nextjs/next-legacy-sass)
2. 윈도우에서 pnpm 패키지 매니저가 느린 이유에 대한 서치. [Windows에서 pnpm이 느린 이유에 대한 서치](/docs/robust-project-structure/pnpm-is-slow)
3. prettier + eslint를 버리고 biome을 사용한 이유.  [ESLint V9 - 에러가 IDE에서 표시되지 않는 경우](/docs/robust-project-structure/biome)
5. post react query [Tanstack Query에서 POST 요청을 사용해도 되는가?](/docs/react/tanstack-query-post)
6. git pull vs git rebase 번역 [git rebase와 git pull의 차이](/docs/robust-project-structure/git-rabase-vs-git-pull)
7. Nextjs 스크롤 위치 유지하기 [Nextjs - scroll 위치 유지하기](/docs/nextjs/next-scroll-restoration)
8. Nextjs SEO - [Next sitemap](/docs/nextjs/next-sitemap)

이런저런 작업들을 통해 깨달은 것은 다음과 같았다. 
최대한 개발 속도를 끌어올리기 위해 Nextjs 구조에서 최대한 react스럽게 구현할 수 있도록 구조를 잡았지만, 프레임워크의 의도를 거스르는 것은 결코 좋은 선택이 아니라는 것이었다.

예를 들어서 모든 page에 **'use client'** 을 사용하더라도, 실제로는 모든 페이지가 react router 처럼 작동하는 것이 아니라, Nextjs router action -> Nextjs 서버 -> layout.tsx -> page.tsx(리액트 번들 다운로드) 의 프로세스가 일어나기 때문에 위 스크롤 위치가 저장되지 않는 것같은 사이드이펙트가 일어날 수 있다는 것이다.

### Limitations


해당 프로젝트를 진행하며 느낀 아쉬움은 전체적인 비효율 및 주인 의식의 부재였다.

- 기획은 기획이, 데이터는 백엔드가, 클라이언트와의 대화는 PM이 

이 프로젝트의 메인 화면은 로그인 여부/유저 롤의 여부에 따라 다른 요소를 보여주는 것이 핵심이었다.

Nextjs 구조에 맞게 다이어그램을 만들고 구현을 시작했다. 다만 내가 받은 기획 문서에는 no-data와 loading 스테이트가 존재하지 않았다. 그래서 개발한 뒤 테스트 과정을 통해 수정사항을 확정하고, no-data와 loading 상태의 ui를 개발하게 되었다.

지금까지 내가 경험한 프로젝트에서 사람의 실수가 없는 프로젝트란 존재하지 않았다. 그런 경우 빠르게 피드백이 되어 바뀐 사양에 빠르게 대응할 수 있는 agile한 방식이 좋다고 생각한다.

- 코드 오너쉽의 부재

이 프로젝트의 코드 관리 방식은 main과 자식 브랜치 모두 git pull로 서로 주고받는 방식이었다. 물론 해당 프로젝트는 완성 후 인수인계하면 끝나는 프로젝트였다고 하더라도, merge commit을 남발하는 것이 앞으로의 ci/cd에 도움이 되지는 않는다고 느꼈다. 팀과 나 자신의 성장을 위해서라면 더더욱.

### 프로덕트와 개발자 자신의 끊임없는 loop

5개월 동안 이 프로젝트를 개발하면서, SI 업계에 대한 이해, AI 프롬프팅, 내 자신의 Nextjs 및 웹 서비스에 대한 이해도... 많은 것에 대해 배울 수 있었다.

무엇보다 중요하다고 생각하는 것은 내가 생각하는 개발, 내가 좋아하는 개발의 의미를 재정의한 것이었다.
### 초심으로 돌아가기

개발을 처음 배웠을 때 본 다이어그램에서는 이렇게 소개한다. 기획, 분석, 디자인, 구현, 테스팅 및 배포, 유지보수, 그리고 피드백을 통한 추가 피쳐 혹은 원래 피쳐의 재기획...

이 루프를 통해서, 프로덕트와 개발자인 나 자신 또한 계속해서 고통과 보람, 경험을 통해 성장한다. 나는 계속해서 성장하고 싶고 내 앞에 닥친 것이 AI 혁명이든, 경제 위기이든 주저하지 않고 도전하려 한다. 나는 개발자니까.

### Limitations

- 모든 페이지가 use client 위주였음에도 react 19의 use 훅을 사용하지 못한 것은 아쉽다.
- 다만 팀원의 러닝커브를 생각해야했기 때문에 실제로 리액트스럽게 구조를 짜는 것을 중점에 두었다.
- 실제로 메인 페이지는 내가 생각하기에 모범적인 nextjs 구조 server component가 client components를 렌더하는 구조로 작업하였음.
- 기획적으로 정의되어 있지 않았고, 개발적으로 시간이 부족했기에 no data 케이스와 컴포넌트 별 로딩을 다 잡지 못했던 점이 아쉽다.,
- si 업체의 한계 - 일단 완성했다고 합의하면 끝이다.에 대한 아쉬움
- git 역시 앞으로 더 나은 케이스를 경험하고 싶다.

### My thoughts

- nextjs를 from scratch에서 써본 것은 처음이라 프레임워크에 대한 이해도를 많이 끌어올릴 수 있었음.
- 백엔드의 제약사항 - next auth 및 next 이해도
- css 상 제약사항 - next의 이해도
- 내가 경험한 케이스가 SI 자체인가, 그렇게 생각하지는 않지만, 개발자로써 지향하는 바와 팀적인 문화와 맞지 않았음.
- git에 대해서는 나 역시 올바른 git flow에 대한 경험이 많지 않았다. 이번 프로젝트에서 pull을 사용해서 일어났던 이슈들. ex) 코드 overriding을 줄이기 위한 최적의 방법을 생각하는 것이 좋겠다.
- 그러나 ai에 관련한 회사의 방침은 확실히 앞으로 개발자의 롤을 잘 반영했다고 생각한다. ai에 대해서는 계속 공부를 해야 한다.
